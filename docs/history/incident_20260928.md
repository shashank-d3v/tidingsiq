# September 28 billing, source completeness, and Bronze archival recovery

> Historical record: September 28–29 observations, not current operating instructions. See the [documentation map](../README.md) for maintained guides.

## Verified diagnosis

Cloud Run service CPU accounted for INR 306.18 in the inspected September report.
Persistent Streamlit WebSocket sessions kept the service active. Request logs
contained 1,401 connections totaling 116.08 connection-hours; concurrent sessions
can overlap, so this does not establish billable instance time.

The daily warehouse run billed about 35 GiB. Three monitoring queries each read
approximately 9 GB by referencing raw JSON payloads; the dlt merge read about
9.32 GB from the unpartitioned Bronze table.

Every September 1–28 source window was incomplete. Most downloaded one of four
files; September 3, 15 and 17 downloaded none. The manifest was treated as an
availability guarantee, bypassing the configured publication lag. Announced
archives could still return 404.

The archive schedule was paused and its job still used dry-run mode. Bronze held
717,405 rows and 9,331,754,244 logical bytes, with history dating to April 7.

## Remediation and measured results

- Applied a 90-minute source publication buffer with bounded asset retries;
  explicit repairs continued to target their exact requested windows.
- Reconstructed reliability metadata for 642,472 historical rows without changing
  original article fields. Typed monitoring reduced the main metrics query's
  dry-run scan to 72,712,463 bytes.
- Verified initial and incremental Parquet exports, including complete
  row/multiplicity comparison and a repeated no-op execution.
- Removed 445,596 checkpoint-covered rows outside the 90-day serving horizon
  after archive verification and creation of a temporary recovery snapshot.
- Repaired 126,541 rows across 34 historical source windows using two bounded
  merges rather than a separate full-table merge for every window.
- Final September 29 pipeline verification passed all nine assets and 121
  quality checks; live ingestion downloaded all four files with no malformed rows.
- The final measured pipeline billed 5.933 GiB, about 83.1% below the original
  35.108 GiB run. One-time repair, archive and migration scans were excluded.
- Reporting was healthy and pipeline, report and twice-daily archive schedules
  were enabled. These are rollout observations, not current live-state checks.

Logical scan reduction does not imply immediate physical storage reclamation:
BigQuery time travel and temporary snapshots can continue to occupy storage.

## Archive and recovery lessons

The incremental worker exports `[checkpoint, UTC midnight - 45d)`, acquires a
GCS generation-conditional lock, stages an immutable source snapshot, compares
exported row multiplicity, writes a manifest and then advances the checkpoint.
Readers follow the bootstrap index and committed manifest chain. Failed exports
and uncommitted manifests do not belong to the archive; zero-row manifests have
no Parquet objects.

Every source replacement or backfill needs a fresh `ingested_at`. Historical
in-place mutations require separate reconciliation. Verify a crashed worker has
stopped before removing its exact lock generation. Archive objects have a
365-day lifecycle; they are not permanent historical storage. Restoration must
select the newest version per `source_record_id` and reapply metadata migrations.

Pruning is separate from export: preserve at least 90 days and any rows whose
publication dates remain inside Silver's horizon. The default deletion cap is
20,000 rows, rechecked transactionally. Larger recovery operations require a
separately bounded procedure. Never restore a whole old snapshot over newer
source versions; merge only identified missing records.

Use the maintained [archive and repair procedures](../operations_runbook.md)
for current commands, runtime settings and verification.

## Reporting correction — September 29

An additive, daily-partitioned `bronze.gdelt_ingestion_attempts` ledger made empty
source-fetch attempts visible to monitoring. Backfill-only history can now
produce a metrics row with unknown live-ingestion fields. The ledger certifies
source-fetch outcomes, not subsequent warehouse-load success.

All 127 automated tests passed locally and in the Linux runtime image. BigQuery
fixtures covered backfill-only history, an empty attempt after success and
recovery afterward. The final canary passed nine assets and 119 checks; two
non-null checks were removed because live metrics must allow unknown values.
Ingestion and reporting releases preserved existing identities and runtime
settings; the archive release remained independent.
